# 2026-08-29 — two real bugs caught by CLI tests

Both caught by `tests/test_cli.py` on first run, before either reached a
person. Recording because both are the kind of bug that's easy to write
again without noticing.

## `--db` silently ignored before the subcommand

`_build_parser` originally defined `--db` on a shared `common` parser and
passed `parents=[common]` to *both* the top-level parser and every
subparser, so `hirogari --db X.db lift ...` would silently use
`./hirogari.db` instead. Root cause: argparse's subparser dispatch
(`_SubParsersAction.__call__`) parses the chosen subcommand into a
*fresh* namespace, then copies every one of that subparser's own actions
onto the outer namespace — defaults included. With `--db` duplicated on
both levels, the subparser's default silently overwrote whatever the top
-level parser had already set, unless the user repeated `--db` *after*
the subcommand too.

Caught because `test_lift_end_to_end_table_output` (in `tests/test_cli.py`)
seeded a project into one `tmp_path` database and then saw a stray event
from an *earlier* test in the results — both tests were silently writing
to and reading from `./hirogari.db` in the real working directory instead
of their own `tmp_path` databases, because `--db` never took effect.
Fixed by putting `--db` only on the top-level parser (see the comment in
`cli.py`'s `_build_parser`), which also means `--db` must come before the
subcommand name — a normal argparse convention, not a limitation worth
working around.

## `print_table`/`print_json` defaulted `file=sys.stdout` at import time

```python
def print_json(rows, file: TextIO = sys.stdout) -> None: ...
```

looks reasonable but is wrong: a parameter default is evaluated *once*,
when the function is defined (i.e. when `output.py` is first imported) —
not per call. It permanently binds whatever `sys.stdout` happened to be
at import time, so later stdout redirection (pytest's `capsys`, a shell
pipe replacing the stream object, anything) is invisible to it. The
builtin `print()` avoids this by special-casing `file=None` internally to
mean "look up `sys.stdout` now"; `print_table`/`print_json` now do the
same explicitly (`file: TextIO | None = None`, resolved inside the
function body).

Caught because three CLI tests asserting on `capsys`-captured output came
back empty even though the (correct) data visibly printed during the test
run — the output was going to the *real* stdout, bypassing the test's
capture entirely.
